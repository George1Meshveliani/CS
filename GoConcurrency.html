Go — The Language Built for Concurrency

Go (Golang) was designed from the ground up with concurrency as a first-class citizen. While languages like Java and C++ bolt threading on top of a sequential model, Go's concurrency primitives — goroutines and channels — are baked into the language syntax itself. The famous Go proverb captures the philosophy:

"Do not communicate by sharing memory; instead, share memory by communicating." — Rob Pike

1. Why Go Wins at Concurrency

To understand why Go excels, let's compare how concurrency is handled across popular languages:

Language Concurrency model Unit cost Communication
C / C++ OS threads (pthreads) ~1–8 MB stack per thread Shared memory + mutexes (error-prone)
Java OS threads (JVM) ~256 KB – 1 MB per thread synchronized blocks, Executors
Python GIL-limited threads / asyncio ~8 MB; GIL blocks true parallelism Queues, asyncio event loop
Node.js Single-threaded event loop N/A (no real parallelism) Callbacks / Promises / async-await
Go Goroutines (M:N scheduling) ~2–4 KB starting stack Channels (CSP model)

A Go program can spin up millions of goroutines on a laptop — something impossible with OS threads. This is the core competitive advantage.

2. Goroutines — Lightweight Threads

A goroutine is a function executing concurrently with other goroutines in the same address space. You launch one with the go keyword. That's it. 

package main

import (
    "fmt"
    "time"
)

func greet(name string) {
    fmt.Println("Hello,", name)
}

func main() {
    go greet("Alice")   // runs concurrently
    go greet("Bob")     // runs concurrently
    go greet("Carol")   // runs concurrently

    // main must wait — otherwise goroutines are killed when main exits
    time.Sleep(100 * time.Millisecond)
    fmt.Println("Done")
}
Why are goroutines so cheap? They start with a ~2 KB stack (vs ~1 MB for an OS thread). The stack grows and shrinks dynamically as needed. You can have 100,000+ goroutines running on a single machine.

Goroutine Lifecycle

WaitGroup — Proper Synchronization

Using time.Sleep to wait for goroutines is a hack. The correct tool is sync.WaitGroup, which counts outstanding goroutines and blocks until all finish. 

package main

import (
    "fmt"
    "sync"
)

func worker(id int, wg *sync.WaitGroup) {
    defer wg.Done() // signal completion when this function returns
    fmt.Printf("Worker %d starting\n", id)
    // simulate work
    fmt.Printf("Worker %d done\n", id)
}

func main() {
    var wg sync.WaitGroup

    for i := 1; i <= 5; i++ {
        wg.Add(1)          // increment counter before launching goroutine
        go worker(i, &wg)  // pass pointer — WaitGroup must not be copied
    }

    wg.Wait() // block until counter reaches zero
    fmt.Println("All workers done")
}

3. Channels — Typed Communication Pipes

A channel is a typed conduit through which goroutines send and receive values. Channels are the primary mechanism for goroutines to communicate safely without explicit locks. 

// Create a channel
ch := make(chan int)       // unbuffered — synchronous
ch := make(chan int, 10)   // buffered capacity 10 — asynchronous up to capacity

// Send (blocks until receiver is ready for unbuffered)
ch <- 42

// Receive (blocks until sender sends for unbuffered)
value := <-ch

// Close signals no more values will be sent
close(ch)

// Range over channel — reads until closed
for v := range ch {
    fmt.Println(v)
}

Direction-typed Channels

Go lets you restrict a channel to send-only or receive-only in function signatures — a compile-time safety feature that expresses intent clearly: 

func produce(ch chan<- int) {  // send-only
    for i := 0; i < 5; i++ {
        ch <- i
    }
    close(ch)
}

func consume(ch <-chan int) {  // receive-only
    for v := range ch {
        fmt.Println(v)
    }
}

func main() {
    ch := make(chan int, 5)
    go produce(ch)
    consume(ch)
}

The select Statement — Multiplexing Channels

select is like a switch for channels — it blocks until one of its cases can proceed, then executes that case. If multiple are ready, it picks one at random (fair scheduling). 

func main() {
    ch1 := make(chan string)
    ch2 := make(chan string)

    go func() { ch1 <- "one" }()
    go func() { ch2 <- "two" }()

    for i := 0; i < 2; i++ {
        select {
        case msg := <-ch1:
            fmt.Println("Received from ch1:", msg)
        case msg := <-ch2:
            fmt.Println("Received from ch2:", msg)
        }
    }
}

// select with timeout pattern:
select {
case result := <-resultCh:
    fmt.Println("Got result:", result)
case <-time.After(2 * time.Second):
    fmt.Println("Timed out!")
}

// select with default (non-blocking check):
select {
case msg := <-ch:
    fmt.Println("Got:", msg)
default:
    fmt.Println("No message ready")
}

4. Concurrency Patterns

4.1 Pipeline

Chain stages together where each stage is a goroutine that reads from an input channel and writes to an output channel. Data flows through like water in a pipe. 

// Stage 1: generate numbers
func generate(nums ...int) <-chan int {
    out := make(chan int)
    go func() {
        for _, n := range nums {
            out <- n
        }
        close(out)
    }()
    return out
}

// Stage 2: square each number
func square(in <-chan int) <-chan int {
    out := make(chan int)
    go func() {
        for n := range in {
            out <- n * n
        }
        close(out)
    }()
    return out
}

func main() {
    // Connect pipeline: generate → square → print
    c := generate(2, 3, 4, 5)
    out := square(c)

    for v := range out {
        fmt.Println(v)  // 4, 9, 16, 25
    }
}

4.2 Fan-Out / Fan-In

Fan-out: distribute work across multiple goroutines to parallelize CPU-bound or I/O-bound tasks. Fan-in: merge multiple result channels into one. 

// Fan-in: merge multiple channels into one
func merge(channels ...<-chan int) <-chan int {
    var wg sync.WaitGroup
    merged := make(chan int)

    // start one goroutine per input channel
    output := func(c <-chan int) {
        defer wg.Done()
        for v := range c {
            merged <- v
        }
    }

    wg.Add(len(channels))
    for _, c := range channels {
        go output(c)
    }

    // close merged when all inputs are drained
    go func() {
        wg.Wait()
        close(merged)
    }()

    return merged
}

func main() {
    in := generate(1, 2, 3, 4, 5, 6, 7, 8)

    // fan-out: two workers each receive from in
    c1 := square(in)
    c2 := square(in)

    // fan-in: merge results
    for result := range merge(c1, c2) {
        fmt.Println(result)
    }
}

4.3 Worker Pool

Limit the number of concurrent goroutines to avoid overwhelming the system. A fixed pool of workers reads jobs from a shared channel. 

func workerPool(numWorkers, numJobs int) {
    jobs    := make(chan int, numJobs)
    results := make(chan int, numJobs)

    // start fixed pool of workers
    for w := 1; w <= numWorkers; w++ {
        go func(id int) {
            for j := range jobs {
                result := j * j   // simulate work
                results <- result
            }
        }(w)
    }

    // send jobs
    for j := 1; j <= numJobs; j++ {
        jobs <- j
    }
    close(jobs)

    // collect results
    for r := 1; r <= numJobs; r++ {
        fmt.Println(<-results)
    }
}

func main() {
    workerPool(3, 9)  // 3 workers, 9 jobs
}

4.4 Done Channel (Cancellation)

Use a done channel to signal goroutines to stop. This is the idiomatic Go approach before context was added to the standard library. Modern code uses context.Context for the same purpose. 

func generator(done <-chan struct{}) <-chan int {
    out := make(chan int)
    go func() {
        defer close(out)
        for i := 0; ; i++ {
            select {
            case out <- i:
            case <-done:  // stop when signalled
                return
            }
        }
    }()
    return out
}

func main() {
    done := make(chan struct{})
    out  := generator(done)

    // read 5 values then cancel
    for i := 0; i < 5; i++ {
        fmt.Println(<-out)
    }
    close(done) // signal all goroutines to stop
}

// Modern equivalent using context:
ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
defer cancel()
// pass ctx to goroutines and check ctx.Done()

5. The sync Package

While channels are the idiomatic way to communicate, the sync package provides lower-level primitives for cases where shared memory access is cleaner.

5.1 Mutex — Protecting Shared State

type SafeCounter struct {
    mu sync.Mutex
    v  map[string]int
}

func (c *SafeCounter) Inc(key string) {
    c.mu.Lock()
    defer c.mu.Unlock()  // always unlock, even if panic occurs
    c.v[key]++
}

func (c *SafeCounter) Value(key string) int {
    c.mu.Lock()
    defer c.mu.Unlock()
    return c.v[key]
}

func main() {
    c := SafeCounter{v: make(map[string]int)}
    var wg sync.WaitGroup

    for i := 0; i < 1000; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            c.Inc("key")
        }()
    }
    wg.Wait()
    fmt.Println(c.Value("key")) // always 1000
}

5.2 RWMutex — Multiple Readers, One Writer

type Cache struct {
    mu   sync.RWMutex
    data map[string]string
}

func (c *Cache) Get(key string) (string, bool) {
    c.mu.RLock()         // multiple goroutines can hold RLock simultaneously
    defer c.mu.RUnlock()
    v, ok := c.data[key]
    return v, ok
}

func (c *Cache) Set(key, value string) {
    c.mu.Lock()          // exclusive lock for writes
    defer c.mu.Unlock()
    c.data[key] = value
}

5.3 sync.Once — Initialize Exactly Once

var (
    instance *DB
    once     sync.Once
)

func GetDB() *DB {
    once.Do(func() {
        instance = &DB{} // called exactly once, even across goroutines
    })
    return instance
}

5.4 sync.Map — Concurrent Map

var m sync.Map

// Store
m.Store("key", "value")

// Load
if v, ok := m.Load("key"); ok {
    fmt.Println(v.(string))
}

// LoadOrStore — atomic check-and-set
actual, loaded := m.LoadOrStore("key", "default")

// Delete
m.Delete("key")

// Range
m.Range(func(k, v interface{}) bool {
    fmt.Println(k, v)
    return true // returning false stops iteration
})

5.5 Atomic Operations

import "sync/atomic"

var counter int64

// Increment atomically (no mutex needed for simple counters)
atomic.AddInt64(&counter, 1)

// Read atomically
val := atomic.LoadInt64(&counter)

// Compare-and-swap (CAS) — the building block of lock-free algorithms
swapped := atomic.CompareAndSwapInt64(&counter, old, new)
When to use channels vs sync primitives:
  • Channels: passing ownership of data, signalling events, pipelines, producer-consumer patterns.
  • Mutex / Atomic: protecting a struct's internal state, simple counters, caches — when the shared state is too fine-grained to pass through channels.

6. Common Pitfalls

Goroutine Leak

A goroutine that is blocked forever waiting on a channel no one writes to — it never gets garbage collected.

// BAD: goroutine leaks if nobody reads from ch
func leak() {
    ch := make(chan int)
    go func() {
        ch <- 1  // blocks forever if nobody receives
    }()
    // function returns, ch goes out of scope, goroutine is stuck
}

// GOOD: use a done channel or context for cancellation
func noLeak(ctx context.Context) {
    ch := make(chan int, 1)
    go func() {
        select {
        case ch <- compute():
        case <-ctx.Done():  // bail out on cancellation
        }
    }()
}

Race Condition

// BAD: unsynchronized access
var count int
go func() { count++ }()
go func() { count++ }()

// GOOD: use sync/atomic or mutex
var count int64
go func() { atomic.AddInt64(&count, 1) }()
go func() { atomic.AddInt64(&count, 1) }()

// Detect races at test/run time:
// go test -race ./...
// go run -race main.go

Deadlock

// BAD: two goroutines waiting on each other
ch1 := make(chan int)
ch2 := make(chan int)

go func() {
    <-ch1   // waits for ch1
    ch2 <- 1
}()

<-ch2   // waits for ch2 — but nobody sends to ch1 first!
ch1 <- 1  // never reached

// Rule: always ensure every send has a corresponding receive.

7. Concurrency vs Parallelism

"Concurrency is about dealing with lots of things at once. Parallelism is about doing lots of things at once." — Rob Pike

A Go program with goroutines is concurrent by design. Whether it runs in parallel depends on GOMAXPROCS (default = number of CPU cores). You can set it at runtime: 

import "runtime"

func init() {
    runtime.GOMAXPROCS(runtime.NumCPU()) // default since Go 1.5
}

// Check how many goroutines are running:
fmt.Println(runtime.NumGoroutine())

Practice Problems

Problem 1: Concurrent Sum

Easy Goroutines + WaitGroup

Given a slice of integers, split it into N equal chunks and sum each chunk concurrently using goroutines. Collect partial sums and return the total. Use sync.WaitGroup and a buffered channel to collect results. 

package main

import (
    "fmt"
    "sync"
)

func concurrentSum(nums []int, workers int) int {
    ch  := make(chan int, workers)
    var wg sync.WaitGroup
    chunkSize := (len(nums) + workers - 1) / workers

    for i := 0; i < workers; i++ {
        start := i * chunkSize
        if start >= len(nums) {
            break
        }
        end := start + chunkSize
        if end > len(nums) {
            end = len(nums)
        }
        wg.Add(1)
        go func(chunk []int) {
            defer wg.Done()
            s := 0
            for _, v := range chunk {
                s += v
            }
            ch <- s
        }(nums[start:end])
    }

    // close channel once all workers finish
    go func() {
        wg.Wait()
        close(ch)
    }()

    total := 0
    for partial := range ch {
        total += partial
    }
    return total
}

func main() {
    nums := make([]int, 100)
    for i := range nums {
        nums[i] = i + 1 // 1..100
    }
    fmt.Println(concurrentSum(nums, 4)) // 5050
}

Key ideas: The WaitGroup tracks all goroutines; a goroutine closes the channel once all workers are done; range ch drains results naturally.

Problem 2: Merge K Sorted Channels

Medium Fan-In

You have K channels, each emitting sorted integers in ascending order. Write a function mergeKSorted that returns a single channel emitting all values in sorted order. (Hint: use a min-heap over the channel heads.) 

package main

import (
    "container/heap"
    "fmt"
)

type Item struct {
    val int
    ch  <-chan int
}

type MinHeap []Item

func (h MinHeap) Len() int            { return len(h) }
func (h MinHeap) Less(i, j int) bool  { return h[i].val < h[j].val }
func (h MinHeap) Swap(i, j int)       { h[i], h[j] = h[j], h[i] }
func (h *MinHeap) Push(x interface{}) { *h = append(*h, x.(Item)) }
func (h *MinHeap) Pop() interface{} {
    old := *h
    x := old[len(old)-1]
    *h = old[:len(old)-1]
    return x
}

func mergeKSorted(channels []<-chan int) <-chan int {
    out := make(chan int)
    h   := &MinHeap{}
    heap.Init(h)

    // seed heap with first value from each channel
    for _, ch := range channels {
        if v, ok := <-ch; ok {
            heap.Push(h, Item{v, ch})
        }
    }

    go func() {
        defer close(out)
        for h.Len() > 0 {
            item := heap.Pop(h).(Item)
            out <- item.val
            // pull next value from the same channel
            if v, ok := <-item.ch; ok {
                heap.Push(h, Item{v, item.ch})
            }
        }
    }()
    return out
}

func chanOf(vals ...int) <-chan int {
    ch := make(chan int)
    go func() {
        for _, v := range vals {
            ch <- v
        }
        close(ch)
    }()
    return ch
}

func main() {
    merged := mergeKSorted([]<-chan int{
        chanOf(1, 4, 7),
        chanOf(2, 5, 8),
        chanOf(3, 6, 9),
    })
    for v := range merged {
        fmt.Print(v, " ") // 1 2 3 4 5 6 7 8 9
    }
}

Key ideas: Min-heap gives O(log K) per element. A dedicated goroutine drives the merge so mergeKSorted returns immediately. The output channel is closed when the heap drains.

Problem 3: Rate Limiter

Medium Ticker + select

Implement a token-bucket rate limiter. The bucket holds up to capacity tokens. Tokens are added at rate per second. Requests must acquire a token to proceed; if none are available, they wait. Use time.Ticker and a goroutine. 

package main

import (
    "fmt"
    "time"
)

type RateLimiter struct {
    tokens   chan struct{}
}

func NewRateLimiter(rate, capacity int) *RateLimiter {
    rl := &RateLimiter{
        tokens: make(chan struct{}, capacity),
    }
    // fill bucket initially
    for i := 0; i < capacity; i++ {
        rl.tokens <- struct{}{}
    }
    // refill goroutine
    go func() {
        ticker := time.NewTicker(time.Second / time.Duration(rate))
        defer ticker.Stop()
        for range ticker.C {
            select {
            case rl.tokens <- struct{}{}: // add token if space available
            default:                      // drop if bucket full
            }
        }
    }()
    return rl
}

// Wait blocks until a token is available.
func (rl *RateLimiter) Wait() {
    <-rl.tokens
}

// Allow returns true immediately if a token is available.
func (rl *RateLimiter) Allow() bool {
    select {
    case <-rl.tokens:
        return true
    default:
        return false
    }
}

func main() {
    limiter := NewRateLimiter(2, 5) // 2 tokens/sec, capacity 5

    for i := 1; i <= 8; i++ {
        limiter.Wait()
        fmt.Printf("Request %d processed at %s\n", i, time.Now().Format("15:04:05.000"))
    }
}

Key ideas: The buffered channel IS the bucket. Adding a token = sending to the channel. Consuming a token = receiving. The default in the refill goroutine silently discards tokens when full — elegant overflow handling with no mutex.

Problem 4: Concurrent Web Crawler

Medium Worker Pool + sync.Map

Implement a concurrent web crawler (simplified). Given a root URL, fetch URLs from a Fetcher interface, crawl each discovered URL concurrently (up to N workers), and avoid crawling the same URL twice. Use a worker pool and sync.Map. 

package main

import (
    "fmt"
    "sync"
)

type Fetcher interface {
    Fetch(url string) (body string, urls []string, err error)
}

func Crawl(url string, depth int, fetcher Fetcher) {
    var visited sync.Map
    jobs    := make(chan string, 100)
    var wg sync.WaitGroup

    visit := func(u string) {
        // store returns false if key already existed
        if _, loaded := visited.LoadOrStore(u, true); loaded {
            return
        }
        wg.Add(1)
        jobs <- u
    }

    const workers = 4
    for i := 0; i < workers; i++ {
        go func() {
            for u := range jobs {
                defer wg.Done()
                body, urls, err := fetcher.Fetch(u)
                if err != nil {
                    fmt.Println("Error:", err)
                    continue
                }
                fmt.Printf("found: %s %q\n", u, body)
                for _, link := range urls {
                    visit(link)
                }
            }
        }()
    }

    visit(url) // seed
    wg.Wait()
    close(jobs)
}

Key ideas: sync.Map.LoadOrStore is an atomic "mark-as-visited" gate. The jobs channel decouples discovery from crawling. WaitGroup tracks in-flight pages.

Problem 5: Publish-Subscribe System

Hard Channels + Mutex

Build a thread-safe pub-sub broker. Subscribe(topic) returns a channel that receives all future messages on that topic. Publish(topic, msg) fans the message out to all current subscribers. Unsubscribe removes a channel. 

package main

import (
    "fmt"
    "sync"
)

type Broker struct {
    mu   sync.RWMutex
    subs map[string][]chan string
}

func NewBroker() *Broker {
    return &Broker{subs: make(map[string][]chan string)}
}

func (b *Broker) Subscribe(topic string) <-chan string {
    ch := make(chan string, 16) // buffered to avoid blocking Publish
    b.mu.Lock()
    b.subs[topic] = append(b.subs[topic], ch)
    b.mu.Unlock()
    return ch
}

func (b *Broker) Publish(topic, msg string) {
    b.mu.RLock()
    subscribers := make([]chan string, len(b.subs[topic]))
    copy(subscribers, b.subs[topic]) // copy slice under read lock
    b.mu.RUnlock()

    for _, ch := range subscribers {
        select {
        case ch <- msg:     // deliver if space available
        default:            // skip slow consumers
        }
    }
}

func (b *Broker) Unsubscribe(topic string, sub <-chan string) {
    b.mu.Lock()
    defer b.mu.Unlock()
    subs := b.subs[topic]
    for i, ch := range subs {
        if ch == sub {
            b.subs[topic] = append(subs[:i], subs[i+1:]...)
            close(ch)
            return
        }
    }
}

func main() {
    broker := NewBroker()
    ch1    := broker.Subscribe("news")
    ch2    := broker.Subscribe("news")

    var wg sync.WaitGroup
    for _, ch := range []<-chan string{ch1, ch2} {
        wg.Add(1)
        go func(c <-chan string) {
            defer wg.Done()
            for msg := range c {
                fmt.Println("received:", msg)
            }
        }(ch)
    }

    broker.Publish("news", "Go 1.23 released!")
    broker.Publish("news", "New generics feature")

    broker.Unsubscribe("news", ch1)
    broker.Unsubscribe("news", ch2)
    wg.Wait()
}

Key ideas: RWMutex lets many goroutines read the subscriber list simultaneously. Copy the slice under read lock before iterating, so slow subscribers don't block others. Buffered subscriber channels + default in select = non-blocking fan-out (slow consumers are dropped, not stalled).

Problem 6: Semaphore from Channels

Easy Buffered Channel

Implement a counting semaphore using only a buffered channel. The semaphore must support Acquire() (blocking) and Release(). Use it to limit concurrent database connections to at most 5. 

package main

import "fmt"

type Semaphore chan struct{}

func NewSemaphore(n int) Semaphore {
    return make(Semaphore, n)
}

func (s Semaphore) Acquire() { s <- struct{}{} }
func (s Semaphore) Release() { <-s }

// =============================

func queryDB(id int, sem Semaphore) {
    sem.Acquire()
    defer sem.Release()
    fmt.Printf("DB query %d running (concurrent: %d/5)\n", id, len(sem))
    // simulate query
}

func main() {
    sem := NewSemaphore(5) // max 5 concurrent DB connections
    var done = make(chan struct{})

    for i := 1; i <= 20; i++ {
        go func(id int) {
            queryDB(id, sem)
        }(i)
    }
    // in real code: use WaitGroup to wait for all
    <-done
}

Key ideas: A buffered channel of capacity N acts as a semaphore. Sending = acquire (blocks when full). Receiving = release (makes room). len(sem) tells you how many slots are taken.
