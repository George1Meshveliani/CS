1. What is Object-Oriented Programming?

Object-Oriented Programming is a programming paradigm that organizes software around objects — bundles of data (fields / attributes) and behavior (methods / functions) that model real-world or abstract entities.

Core Idea: Instead of writing a program as a sequence of instructions that manipulate raw data, OOP groups related data and the operations on that data together into a single unit called an object. Objects communicate by calling each other's methods.

Procedural vs Object-Oriented

Procedural (C, Pascal)Object-Oriented (C++, Java, Python)
Program = sequence of procedures/functionsProgram = collection of objects interacting
Data and logic are separateData and logic are bundled together
Hard to model real-world entities naturallyNaturally maps to real-world concepts
Code reuse via copy-paste or function librariesCode reuse via inheritance and composition
No built-in access controlAccess modifiers protect internal state
Harder to scale and maintainScales better; changes localized to classes

Historical Context

OOP emerged in the 1960s with Simula (the first OO language), was popularized by Smalltalk in the 70s, and became mainstream through C++ (1983), Java (1995), and Python (1991). Today it is the dominant paradigm for large-scale software.

Mental Model: Think of a Car. It has data (color, speed, fuel level) and behavior (accelerate, brake, refuel). An object bundles these together. You interact with a car through its interface (pedals, steering wheel) without needing to know the internal engine mechanics — that's encapsulation.

2. The Four Pillars of OOP

🔒

Encapsulation

Bundling data and methods that operate on that data within one unit; hiding internal details via access control.

🧬

Inheritance

A class (child) can acquire properties and behaviors of another class (parent), enabling code reuse and hierarchical relationships.

🎭

Polymorphism

The same interface or method name can behave differently depending on the object type it is called on (overloading & overriding).

🎨

Abstraction

Exposing only relevant details to the outside world; hiding complex implementation behind a clean interface.

Remember: These four concepts work together. Encapsulation protects data; Abstraction simplifies interfaces; Inheritance reuses code; Polymorphism makes code flexible.

3. Classes & Objects in C++

A class is a blueprint (type definition). An object is an instance of that class allocated in memory. Think of a class as the cookie cutter; objects are the cookies.

Syntax overview: class ClassName { access_specifier: members; };
Members include data members (fields) and member functions (methods).

Basic Class Example

#include <iostream> #include <string> using namespace std; class Car { private: // hidden from outside string brand; int speed; double fuel; public: // accessible interface // Constructor Car(string b, int s, double f) : brand(b), speed(s), fuel(f) {} // Methods (behavior) void accelerate(int delta) { speed += delta; fuel -= delta * 0.1; } void describe() const { cout << brand << " | speed: " << speed << " km/h | fuel: " << fuel << "L\n"; } // Getters (controlled access to private data) string getBrand() const { return brand; } int getSpeed() const { return speed; } }; int main() { Car myCar("Toyota", 0, 50.0); // create object on stack myCar.accelerate(60); myCar.describe(); // Toyota | speed: 60 km/h | fuel: 44L Car* pCar = new Car("BMW", 0, 60.0); // heap object pCar->accelerate(100); pCar->describe(); delete pCar; return 0; }

Stack vs Heap Objects

Modern C++: Prefer std::unique_ptr<Car> or std::shared_ptr<Car> over raw new/delete to avoid memory leaks.

The this Pointer

Inside every non-static member function, this is a pointer to the calling object. It is used to disambiguate when parameter names shadow member names, or to return the object itself (method chaining).

class Counter { int count; public: Counter(int count) : count(count) {} // initializer list avoids ambiguity Counter& increment() { ++(this->count); return *this; // enables chaining: c.increment().increment() } void print() const { cout << count << "\n"; } };

4. Access Modifiers — private, protected, public

Access modifiers control who can see and touch a class member. C++ has three levels:

🔒 private

  • Accessible only within the same class
  • Not visible to derived classes
  • Not visible to outside code
  • Default in class keyword
Strictest

🛡️ protected

  • Accessible within the same class
  • Accessible in derived (child) classes
  • Not visible to outside code
  • Key for inheritance hierarchies
Middle

🌐 public

  • Accessible from anywhere
  • Forms the class's public interface
  • Default in struct keyword
  • Expose only what's necessary
Most Open

Access Modifier Summary Table

Same class (own methods)✅✅✅
Derived class (child)❌✅✅

Code Demonstration

class Animal { private: int heartRate; // only Animal's own methods can touch this protected: string name; // Animal + its children can read/write int age; public: Animal(string n, int a, int hr) : name(n), age(a), heartRate(hr) {} void breathe() { heartRate += 1; // OK: inside Animal cout << name << " breathes. HR=" << heartRate << "\n"; } string getName() const { return name; } }; class Dog : public Animal { public: Dog(string n, int a) : Animal(n, a, 80) {} void bark() { // name and age are protected — accessible here cout << name << " (age " << age << ") barks!\n"; // heartRate is private — NOT accessible here (compile error if tried) } }; int main() { Dog d("Rex", 3); d.bark(); // OK d.breathe(); // OK — public method inherited // d.name = "x"; // Error: protected, not accessible outside // d.heartRate = 0; // Error: private return 0; }

struct vs class in C++

The only difference between struct and class in C++ is the default access level:
  • struct: members are public by default
  • class: members are private by default
Convention: use struct for plain data aggregates (POD types), class for objects with invariants and behavior.

Inheritance Access Specifiers

When inheriting, the access specifier on the : controls how the parent's members appear in the child:

Parent memberpublic inheritanceprotected inheritanceprivate inheritance

95% rule: Almost always use public inheritance. private inheritance means "implemented in terms of" and is rarely needed (prefer composition instead).

Friend Functions & Classes

A friend declaration grants a specific external function or class full access to all private and protected members — it is a deliberate exception to encapsulation.

class BankAccount { double balance; // private public: BankAccount(double b) : balance(b) {} friend void audit(const BankAccount&); // friend declaration }; void audit(const BankAccount& acc) { cout << "Balance: " << acc.balance << "\n"; // accesses private directly }

5. Constructors & Destructors

A constructor is a special method called automatically when an object is created. A destructor is called when the object goes out of scope or is deleted. Together they manage the lifetime of resources (the RAII pattern).

class Resource { int* data; int size; public: // Default constructor Resource() : data(nullptr), size(0) { cout << "Default ctor\n"; } // Parameterized constructor Resource(int n) : size(n) { data = new int[n]; cout << "Alloc ctor (n=" << n << ")\n"; } // Copy constructor (deep copy) Resource(const Resource& other) : size(other.size) { data = new int[size]; copy(other.data, other.data + size, data); cout << "Copy ctor\n"; } // Move constructor (C++11) Resource(Resource&& other) noexcept : data(other.data), size(other.size) { other.data = nullptr; other.size = 0; cout << "Move ctor\n"; } // Destructor — always called when object dies ~Resource() { delete[] data; cout << "Destructor (size=" << size << ")\n"; } };

The Rule of Three / Five / Zero

RuleWhenWhat to define
Rule of ZeroClass manages no raw resourcesDefine nothing — rely on compiler defaults
Rule of ThreeClass manages a raw resource (pre-C++11)Destructor, Copy constructor, Copy assignment
Rule of FiveMove semantics needed (C++11+)All three above + Move constructor + Move assignment

Constructor Initializer List

Always prefer initializer lists over assignment in constructor body. They initialize members directly — assignment initializes then re-assigns, which is wasteful (especially for non-trivial types). For const members and references, initializer lists are the only option.
// GOOD — initializer list Person(string n, int a) : name(n), age(a) {} // BAD — default-initializes then assigns Person(string n, int a) { name = n; // default string() then operator= age = a; }

Delegating Constructors (C++11)

class Box { int w, h, d; public: Box(int w, int h, int d) : w(w), h(h), d(d) {} Box(int side) : Box(side, side, side) {} // delegates to above Box() : Box(1) {} // delegates again };

6. Inheritance

Inheritance lets a derived class (child) reuse and extend the members of a base class (parent). It models an "is-a" relationship.

Syntax: class Derived : access_specifier Base { ... };
The derived class inherits all non-private members and can add new members or override (replace) virtual methods.

Single Inheritance — Shape Hierarchy

#include <cmath> class Shape { protected: string color; public: Shape(string c) : color(c) {} virtual double area() const { return 0.0; } // virtual — can be overridden void printColor() const { cout << "Color: " << color << "\n"; } virtual ~Shape() {} // virtual destructor — CRUCIAL }; class Circle : public Shape { double radius; public: Circle(double r, string c) : Shape(c), radius(r) {} double area() const override { // override keyword (C++11) return M_PI * radius * radius; } }; class Rectangle : public Shape { double width, height; public: Rectangle(double w, double h, string c) : Shape(c), width(w), height(h) {} double area() const override { return width * height; } }; int main() { Circle c(5.0, "red"); Rectangle r(4.0, 6.0, "blue"); // Polymorphic: same call, different behavior Shape* shapes[] = { &c, &r }; for (auto s : shapes) { s->printColor(); cout << "Area: " << s->area() << "\n"; } }

Constructor Chaining in Inheritance

When a derived object is created, constructors run base-first. Destructors run in reverse order (derived-first). Use the initializer list to pass arguments to the base constructor.

class A { public: A() { cout << "A()\n"; } ~A() { cout << "~A()\n"; } }; class B : public A { public: B() { cout << "B()\n"; } ~B() { cout << "~B()\n"; } }; class C : public B { public: C() { cout << "C()\n"; } ~C() { cout << "~C()\n"; } }; // Creating C: prints A() B() C() // Destroying C: prints ~C() ~B() ~A()

Calling Base Class Methods — BaseClass::method()

class Employee { public: virtual void describe() const { cout << "Employee\n"; } }; class Manager : public Employee { public: void describe() const override { Employee::describe(); // call parent version first cout << " + manages a team\n"; } };

Inheritance vs Composition

Prefer composition over inheritance when the relationship is "has-a" rather than "is-a". Inheritance creates tight coupling — a change to the base class ripples through all children. Composition (embedding objects as members) is more flexible.
// "is-a" — use inheritance class SportsCar : public Car { ... }; // "has-a" — use composition class Car { Engine engine; // Car HAS an Engine Wheels wheels; // Car HAS Wheels };

7. Polymorphism & Virtual Functions

Polymorphism (many forms) means one interface, multiple implementations. C++ has two kinds:

TypeMechanismResolved atExample
Compile-time (static)Function overloading, templates, operator overloadingCompile timeprint(int) vs print(double)
Runtime (dynamic)Virtual functions + pointers/references to baseRuntime (vtable)shape->area() dispatches to the right subtype

How Virtual Functions Work — The vtable

Every class with at least one virtual function gets a hidden vtable (virtual dispatch table) — an array of function pointers. Each object stores a hidden vptr pointing to its class's vtable. When you call base_ptr->virtualMethod(), the runtime looks up the correct function via the vptr — this is dynamic dispatch.

Virtual Destructor — Critical Rule

Always declare the destructor virtual in a base class if you intend to delete derived objects through base pointers. Without it, only the base destructor runs, leaking the derived class's resources (undefined behavior).
class Base { public: virtual ~Base() { cout << "~Base\n"; } // ✅ virtual }; class Derived : public Base { public: ~Derived() { cout << "~Derived\n"; } }; Base* p = new Derived(); delete p; // prints ~Derived then ~Base ✅

Function Overloading vs Overriding

The override and final Keywords (C++11)

class Base { public: virtual void foo(int) {} virtual void bar() {} }; class Derived : public Base { public: void foo(int) override {} // ✅ compiler checks signature matches void bar() final {} // ✅ no further overriding allowed // void foo(double) override {} // ❌ compile error: no matching virtual };

8. Abstract Classes & Pure Virtual Functions

A pure virtual function has no implementation in the base class — it declares a contract that all concrete derived classes must fulfill. A class with at least one pure virtual function is an abstract class; you cannot instantiate it directly.

class ILogger { // abstract "interface" public: virtual void log(const string& msg) = 0; // pure virtual virtual void flush() = 0; virtual ~ILogger() {} }; class ConsoleLogger : public ILogger { public: void log(const string& msg) override { cout << "[LOG] " << msg << "\n"; } void flush() override { cout << "[FLUSH]\n"; } }; class FileLogger : public ILogger { ofstream file; public: FileLogger(string path) : file(path) {} void log(const string& msg) override { file << msg << "\n"; } void flush() override { file.flush(); } }; // Client code depends only on ILogger — not on concrete type void runApp(ILogger& logger) { logger.log("App started"); logger.flush(); }
Interface pattern: In C++ there's no interface keyword (unlike Java/C#). An abstract class with only pure virtual functions and a virtual destructor acts as an interface. Naming convention: prefix with I (e.g., ILogger).

9. Encapsulation in Practice

Encapsulation means keeping an object's internal state private and exposing only a controlled, validated interface. The object is the sole guardian of its own invariants.

Why Encapsulate?

  • Invariant protection: Ensures object state is always valid (e.g., age can't be negative)
  • Flexibility: Change internal representation without breaking callers
  • Reduces coupling: External code depends on the interface, not implementation details

Getter / Setter Pattern with Validation

class Temperature { double celsius; // invariant: -273.15 ≤ celsius public: Temperature(double c) { setCelsius(c); } void setCelsius(double c) { if (c < -273.15) throw invalid_argument("Below absolute zero"); celsius = c; } double getCelsius() const { return celsius; } double getFahrenheit() const { return celsius * 9.0 / 5.0 + 32; } double getKelvin() const { return celsius + 273.15; } };
Key insight: The internal representation could change from celsius to kelvin tomorrow. Since callers use getCelsius() / getFahrenheit() rather than direct field access, zero external code needs updating.

10. Operator Overloading

C++ lets you redefine the behavior of operators (+, ==, <<, etc.) for user-defined types, making objects feel like built-in types.

class Vector2D { public: double x, y; Vector2D(double x, double y) : x(x), y(y) {} // Member operator: left operand is *this Vector2D operator+(const Vector2D& o) const { return { x + o.x, y + o.y }; } Vector2D& operator+=(const Vector2D& o) { x += o.x; y += o.y; return *this; } bool operator==(const Vector2D& o) const { return x == o.x && y == o.y; } // Non-member: stream output (friend so it can access private) friend ostream& operator<<(ostream& os, const Vector2D& v) { return os << "(" << v.x << "," << v.y << ")"; } }; int main() { Vector2D a(1, 2), b(3, 4); Vector2D c = a + b; // calls operator+ cout << c << "\n"; // (4,6) — calls operator<< cout << (a == b) << "\n"; // 0 (false) }
Rules for operator overloading:
  • Cannot change operator arity (number of operands)
  • Cannot create new operators
  • Cannot overload ::, ., .*, ?:
  • Preserve expected semantics — + should feel like addition
  • For symmetric operators (+, ==), prefer non-member functions

11. Multiple Inheritance & the Diamond Problem

C++ allows a class to inherit from multiple base classes. This is powerful but can introduce ambiguity — the infamous Diamond Problem.

The Diamond Problem

// Without virtual inheritance — PROBLEM class A { public: int x; }; class B : public A {}; class C : public A {}; class D : public B, public C {}; D obj; // obj.x = 5; ❌ AMBIGUOUS — is it B::A::x or C::A::x? obj.B::x = 5; // explicit disambiguation obj.C::x = 10; // two separate copies of A!
// With virtual inheritance — SOLUTION class A { public: int x; }; class B : virtual public A {}; // virtual class C : virtual public A {}; // virtual class D : public B, public C {}; // only ONE copy of A D obj; obj.x = 5; // ✅ unambiguous — single shared A

Diamond inheritance — D inherits from both B and C which both inherit from A

Practical advice: Multiple inheritance with data is complex and error-prone. Prefer multiple inheritance of pure interfaces (abstract classes with no data) — this is safe and widely used (similar to Java/C# interfaces).

Quick Reference — C++ OOP Cheatsheet

Class skeleton
class MyClass : public Base { private: // default for class int x; protected: double y; public: MyClass(int x, double y); // ctor virtual ~MyClass(); // dtor void method() const; // const virtual void virt() override;// override static int staticFn(); // static };
Key rules to remember
  • Always virtual ~Base() if used polymorphically
  • Use override — catches signature mismatches
  • Prefer initializer lists in constructors
  • Rule of Five: if you write any of dtor/copy/move, write all five
  • Prefer composition over inheritance
  • Avoid object slicing — use pointers/references for polymorphism
Access cheat-sheet
  • private — same class only
  • protected — same class + children
  • public — everyone
  • friend — named exception
  • struct default = public
  • class default = private
Polymorphism checklist
  • Mark base method virtual
  • Use pointer or reference to base
  • Mark derived method override
  • Virtual destructor in base
  • Don't pass by value (object slicing!)
